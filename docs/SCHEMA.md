# coin-game/1.11.0 schema guide

File: `schema/coin-game.schema.json` (JSON Schema 2020-12). Example: `examples/tan-war.game.json`.
Rule: one JSON file holds the whole game. Printed text, diagrams and bot aids come from it. Nothing else is a source of truth.

## Top-level sections

| Section | Holds |
|---|---|
| `meta` | Schema version, game id, revision, `draft` or `final`, faction count, supplies, credits |
| `brief` | Conflict text, Wikipedia article, overview, sources (`pending`, `read`, `failed`), claims (`historical` or `design`) |
| `factions` | Name, type, color AND symbol, role, pieces (states, supply), actions, resource track |
| `board` | `spaces`, `links` (legal adjacency), `presentation` (drawing positions, kept apart from links) |
| `tracks` | Id, range, start value |
| `setup` | Placements, space attributes (opinion), pools (Available and Out of Play), track values, eligibility |
| `rules` | Sequence of play table, scoring round phases, rulebook text by section |
| `actions` | Operations and Special Activities: cost, legal-space filter, ordered effect steps; optional purpose, rule section, accompanying Operations and max spaces |
| `deck` | Cards (Event with two sides, scoring) and deck preparation piles |
| `victory` | Formula and threshold per faction, check timing, final scoring, tie-breaks |
| `bots` | One bot per faction: objective, measures, Event policy, decision graph, priority tables, dice rule, dry runs |

## Expression language

Used for filters, formulas, conditions and tie-break keys. A value is a literal, `{"var": "..."}` or `{"op": "...", "args": [...]}`.

- Ops: `and or not eq ne gt gte lt lte add sub mul min max count adjCount factionCount sumSpaces anySpace attr canPlace canDo unmoved avail factionAvail`.
- `avail(piece)` (1.11.0): pieces of the type in the Available pool now; effect steps that place or remove change it. `factionAvail(faction)` (1.11.0): the sum of `avail` over every piece the faction owns.
- `unmoved(piece, space|"*", state|"*")` (1.9.0): like `count`, less the pieces that moved into the space in the current Operation (GMT "Guerrillas yet to move").
- `canPlace(piece, space|"*")` (1.8.0): at least 1 of the piece is Available and the space has room under the piece's `maxPerSpace`; `"*"` means some space has room. Other placement rules of a game are not checked.
- `canDo(action, space|"*")` (1.8.0): the space is legal for the action (its `targets` and the `legal` of each top-level choice option; inside an action node with a target, for that target), and the action's faction has Resources for its cost. Use it for GMT rows such as "in 1 space where FARC would Ambush". Another faction's action is read as that faction: `self`, `card.position` and `card.lasting` (from that faction's bot) are its own; `card.hasEffect`, `card.raisesSelf` and `card.lowersEnemy` stay the running bot's, as a dry run sets them.
- `count(piece, space|"*", state|"*")` counts pieces. `factionCount(faction, space|"*", state|"*")` counts every piece of one faction; the faction can be an id, `$target.id` or `$faction.id`. `adjCount` counts in linked spaces. `sumSpaces` and `anySpace` run an expression once per space.
- Variables: `eligible`, `self.resources`, `resources.<faction>`, `eligible.<faction>`, `score.<faction>` (its victory formula now), `margin.<faction>` (score minus threshold), `player.<faction>` (1.11.0: true when a human plays the faction; default: no bot for it), `rivals.maxMargin|minMargin|maxScore|minScore|maxResources|minResources` (over every enemy), `$faction.id|name|type|resources|eligible|score|margin|player` (in an opponent table), `$target.…` (same fields, after an action picked its enemy), `track.<id>`, `card.id|hasEffect|raisesSelf|lowersEnemy|lasting|position`, `turn.position`, `scoring.nextFinal`, `move.count` (only in a move step's `activate.if`; 0 elsewhere), `$space.id|name|type|pop|opinion|control` (control: 1.11.0), `inPlay.<card>` (1.11.0: the lasting card is in play; default none; a dry-run patch sets `inPlay`), `var.<name>`.
- Booleans count as 1 or 0 in `add` and `mul`.

## Effect steps (no-code mechanics)

Ordered list. Fields per op come from `src/ops.mjs`; the schema's `$defs.step` is generated from it. No other field is allowed. Optional fields in brackets.

| Op | Fields |
|---|---|
| `place` | piece, count, from (pool), to (where), [state, space, spaces, filter] |
| `remove` | piece, count, to (pool), [state, fallbackPiece, space, spaces, filter, keep] |
| `flip` | piece, from (state), to (state), count, [space, spaces, filter, keep] |
| `move` | piece, count, from (loc), to (loc), [state, filter, activate, keep] (1.9.0: `activate: { if, to }`, read at the destination with `move.count`) |

`keep` (1.11.0 part E) on `move`, `remove` and `flip`: `{ count, if, prefer }`. In each space the pieces leave (each source of a move), the step leaves at least `count` of its piece, all states together; a flip leaves them in its `from` state ("without exposing the last Underground Guerrilla"). `count` is a number or an expression read on that space, such as `add(1, inPlay.<card>)` for GMT "1(2)". `if` (read on that space) limits the rule to some spaces; left out, every space. `prefer`: the step takes other states first, so the kept pieces are in that state when there are enough ("Underground first"). Keep limits the count, not the legal spaces. Plain English: "Leave at least 1 Guerrillas in each space they leave where ..., underground first."
| `shift` | attr (`opinion`), toward (`support` or `opposition`), amount, [space, spaces, filter]. One level per amount, to the ends of the game's scale (1.9.0: 3 or 5 levels) |
| `track` | id (track), delta |
| `gain` | track, amount (number or formula) |
| `pay` | track, amount. The step fails when the track holds less than the amount. |
| `roll` | die (`d6`), store (stores the result as `var.<store>`) |
| `markerSet` | marker (a mutable space attribute, like opinion), value, [space, spaces, filter] |
| `if` | test, then, [else] |
| `choose` | options: each has a label and steps; optional `faction` (1.6.0), `legal` (1.6.0) and `piece` (1.9.0, a piece type of that faction) |

- count: a whole number, `all`, `any`, `moved` or a formula.
- pool: `available` or `outOfPlay`. where: `$space` (the space being resolved), `choose` or a space id. loc: a where value, `adjacent` or a pool.
- spaces: how many spaces to choose. filter: a condition on `$space` for the chosen spaces.
- The validator checks piece, track and space ids, and that each state belongs to its piece.

## Bot decision graph

- Nodes: `condition` (yes and no), `event-check` (yes and no), `action` (`then` and `onEmpty`, optional `linked` Special Activity, optional `parts`), `end` (outcome `none`, `event`, `operation`, `operationSpecial`, `pass`).
- Every non-end node needs both branches. Loops are not allowed. Every node must be reachable.
- Loop pattern (GMT "Loop: Pass", "If loop: Transport"). The graph has no cycles, so a second pass is written out. On the `onEmpty` path of the last Operation, add more action nodes for the same Operations, each with a looser priority table (fewer or wider steps). The last `onEmpty` goes to an `end` node, such as `pass`. Name the nodes and tables so the second pass is clear, for example `Rally (loop)`. No schema field is needed (`docs/proposals/bot-model-gaps.md`, part B).
- Event check order: override for the card id (`force`, `ignore`, `conditional`), else `playIf`. A card needs an effect to be played.
- Override `node` (1.10.0): when the bot plays the card, it runs the steps of the side it plays. Each step that needs a space picks with `node.table` (up to the step's `spaces`, 1 for `choose`), as in a scoring phase. `node.target`, an opponent table, picks the enemy first; a choice runs that enemy's option, and a dry-run result records `target`. No enemy qualifies: the Event runs with no target. The chosen spaces go into `chosen`. Then the bot follows `yes`. Without a node, the Event changes nothing in a dry run. An `ignore` override takes no node. A node whose target table can pick a piece needs the card side's enemy choices at the top level. A card side may hold a piece option on a top-level choice, for that target. A card side may read `$target` when every override node that runs it has a target table.
- `card.lasting` is `momentum`, `capability` or `none`: the `lasting` value of the side this bot plays for the current card (the override's `side`, else `eventPolicy.side`). A dry-run patch may set it in `card`. What a lasting effect does each turn is an engine rule; the side's `text` states it. The Non-Player sheet prints the overrides for lasting cards in a "Momentum, Capability" box, not in the Event Instructions.
- `card.position` (1.8.0): this faction's place in the card's `order` (1 first, 0 not listed). `turn.position` (1.8.0): 1 or 2. A dry-run patch may set either (`card.position`, `turn.position`); `turn.position` is 1 otherwise. GMT "Play Event if FARC symbol first, or 2nd Eligible": `card.position == 1 or turn.position == 2`.
- Step `target` (1.8.0, space tables only): an enemy faction. That step's filter and tie-breaks read `$target` as that faction; it picks only spaces where the action is legal against it; each space it picks runs the action against it. A dry-run result records `targets` (space id to faction) for the Operation's spaces. Other steps keep the node's target, if any. The aid and the Non-Player sheet print "Target: <faction>" on the row.
- Opponent table (`scope: opponent`): picks one enemy faction. Steps and tie-breaks read `$faction`. A step may name an enemy `piece` (1.9.0, GMT "target: Shipments"): it considers only that piece's owner, and the action runs only the choice option with that `faction` and `piece`. Ties left after the lettered tie-breaks go to the die, as for spaces.
- Action node `target`: an opponent table. The bot picks the enemy first; no enemy qualifies means the same as no space (`onEmpty`). The space table and the linked Special Activity read `$target`. A dry-run result records `target`.
- Control (1.11.0 part D): optional `rules.control: { sides, exclude, types }`. A faction or side controls a space when its pieces there outnumber all other pieces. `sides: [{ id, name, factions }]` (2 or more factions) control together, such as COIN = US + ARVN (FITL, A Distant Plain, Colonial Twilight); a faction in no side controls alone (Andean Abyss, Cuba Libre). `exclude` lists pieces that do not count. `types` lists the space types that can be controlled (left out: every space; FITL, A Distant Plain and Andean Abyss leave out LoCs). `$space.control` gives the side id, the faction id or `none`. It needs `rules.control`; a compare (`eq`, `ne`) with it must name a side, a faction or `none`. A side id must not be a faction id or `none`, and a faction is in one side at most. Rules that depend on the space (People Power Activists in Protest spaces) are out of scope. The editor's board preview labels each controlled space at setup; the printed board does not. Plain English: "COIN controls this space", "no one controls this space".
- Action node `budget` (1.11.0 part C): what the node's Operation may spend. `share: [num, den]` spends Resources x num / den, rounded down; `allBelow` spends all Resources when they are below it (needs `share`); `floor` keeps at least that many Resources. Each part is optional; with `share` and `floor`, the smaller spend wins. The share is fixed from the Resources at the start of the Operation and counts what the Operation pays; Resources gained during the Operation do not raise it. The floor is checked against the Resources at each payment. The budget limits the spaces paid per space and the one cost paid per use; with too little to pay, the node is empty (`onEmpty`). A linked Special Activity pays from the full Resources. A Special Activity timed `before` pays first; then the Operation still has its share, within the floor and the Resources left. `canDo` does not read budgets. GMT: "for 2/3↓ of Res max, for all if Res < 9", "do not spend Res such that falling below 41 Res". The bot aid and the Non-Player sheet print it as "Spend at most 2/3 of Resources (round down), or all if Resources are below 9. Keep at least 41 Resources."
- Action node `parts` (1.5.0 part C; rules 1 to 8 confirmed by the owner on 2026-11-21 and 2026-11-22). An optional list of `{ text, table, steps }`: numbered sub-actions in one Operation box, such as GMT Rally "1 flip Underground, 2 place Bases, 3 place Guerrillas". Rules:
  1. Order: the parts run in list order. Each part picks its spaces with its own space table from the Operation's legal spaces (`targets`), on the board the earlier parts left. It then runs its own `steps` once in each space it picked. The Operation's own `steps` do not run.
  2. Cost, `per: "space"`: paid once for each distinct space, over all parts, when a part first picks it. A space that an earlier part already paid for costs nothing again. A part's space limit is its table's limit, capped by the spaces the faction can still pay for (spaces already paid for do not count against it).
  3. Cost, `per: "use"`: paid once, when the first part picks a space. Later parts pay nothing.
  4. Empty: the node is empty only when every part picks no space. Then the path records `<node>:empty`, nothing is paid and the bot follows `onEmpty`. If any part picks a space, the bot follows `then`, also when other parts are empty.
  5. Result: `chosen` lists each distinct space once, in the order the parts first picked it.
  6. With `parts`, the node has no `table` of its own (the validator rejects both). `target` still picks the enemy first; every part reads `$target`.
  7. A linked Special Activity with timing `after` or `during` runs after the last part.
  8. Timing `before`: (a) The empty check comes first: each part's table is tried on the board as it is, before anything runs. If no part finds a legal, affordable space, the node is empty (rule 4) and the Special Activity does not run. (b) Otherwise the linked Special Activity resolves first, on that board. No Operation cost is set aside, because the parts have not picked spaces yet. (c) Then the parts run under rules 1 to 5 on the board the Special Activity left. A space it made illegal or unaffordable is not picked. Nothing is refunded, because nothing was paid for it. If no part picks a space now, the Operation changes nothing, `chosen` is empty and the bot still follows `then`.
- Priority table: numbered steps (`mode: first`, the default: the first step with any match wins; `mode: sequence` with `select: all`: every step in order, each step's matches in tie-break order, until the limit; a step may carry its own `tiebreak`, used for its matches in place of the table's), lettered tie-breaks (`max` or `min`), `select` `one` or `all` (`all` needs a `limit`; leftover ties break by space name).
- Random tie: sort tied spaces by name. Roll one die. With N spaces, die faces split into N equal groups in list order. A tie with no explicit die is an error.
- Linked Special Activity: runs after the Operation when `trigger` is true and the table finds a legal space. `linked` may be one object or a list. A list is tried in order: the first entry whose `trigger` holds and whose table finds a legal space runs, and the rest are skipped. No entry runs: the result is `skipped`. Each entry must accompany the node's Operation and match its Special Activity's timing, and every entry of one list uses the same timing (owner decision, 2026-11-21). A GMT diamond that picks the Special Activity is the `trigger` of the first entry; "if none" is the next entry. A dry run pays the Operation's cost and applies its effect steps first (`src/effects.mjs`), so the trigger, the legal spaces and the table read the board after the Operation (timing `after` or `during`). With timing `before`, the Operation's cost is set aside first, then the Special Activity resolves on the board before the Operation's steps, and the steps apply after it. Chosen spaces that the Special Activity made illegal are dropped from `chosen` and their cost is refunded; if none stay, the Operation changes nothing. Placed and moved pieces use the piece's `defaultState` when a step names no state, and stop at `maxPerSpace`. Example: Tan War `cw.d7`.
- Scoring choices (`bot.scoring`): in each phase an entry names, every step that needs a space (`spaces` with `filter`, or a `choose` space or `move` end) picks with the entry's space table. It takes up to the step's `spaces` (1 for `choose`), capped by the table (`select: one` takes 1). Ties use the lettered tie-breaks and then the die, as for actions. The step then runs once in each chosen space. At most one entry over all bots names a phase. Phases no entry names stay automatic. Owner decisions, 2026-11-21.
- Choices inside effect steps, in dry runs: `choose` takes the first option. Count `any` moves or flips as many as it can. `move` from `adjacent` takes pieces from linked spaces in name order. A `roll` takes the next die of the dry run (none left is an error). A step that needs a player to pick a space (`choose`, or `spaces` with `filter`) is an error, except in a scoring phase that `bot.scoring` names or an Event that an override `node` runs.
- Dry runs: `patch` on the setup state (`eligible`, `players` (1.11.0), `pools.<piece>.available` (1.11.0), `inPlay` (1.11.0), `resources`, `tracks`, `card`, `dice`, `clearPieces`, `spaces.<id>.opinion`, `spaces.<id>.pieces.<piece>`) plus the `expect`ed outcome, path, chosen spaces, side and linked result. Six cases are required: `ineligible`, `event-override`, `no-target`, `tie`, `linked-sa`, `fallback`. The optional case `scoring` runs each phase that `bot.scoring` names, in rules order, on the patched board, and expects `outcome: none`, `path` (the phase ids) and `chosen` (every chosen space, in order).

## Validation

Run `npm run validate`. Errors carry a JSON path, a code, a plain message and the editor to open. A `final` revision needs `confirmedAt` and zero errors. Warnings (such as a pending source) do not block.

## Exports

Run `npm run export` for a folder, or `node src/cli.mjs zip <game.json> <out.zip>` for the same zip the wizard downloads. The kit holds `game.json`, a rulebook, a setup sheet, the board SVG, card sheets, counters, a component list, a print test sheet (50 mm ruler, one card and one counter at true size), a Sequence of Play sheet, a Card and Spaces list, one faction sheet per faction (front in the layout of the printed GMT faction sheets, back with forces, sequence of play and scoring) and one Non-Player sheet per bot (one page in the layout of the printed GMT Non-Player sheets). Per bot: aid (`.md`, `.html`), flowchart (`.mmd` and rendered `.svg`), policy (`.yaml`) and structured data (`.json`). An unconfirmed game marks every file DRAFT.

## Engine contract (frozen)

`coin-game/1.11.0` is frozen. The engine must accept this version. `test/engine.test.mjs` holds a fingerprint of the schema file and fails on any change: a change needs a new version and a `migrate` step.

Rules the schema alone does not say:

- Sequence of play: the first two Eligible factions in the card's faction order act (COIN style), for 2 to 4 factions. Factions that act become Ineligible, except after the choices in `eligibilityAfter.staysEligible`.
- Opinion is one axis per space: +1 is Support, -1 is Opposition. `shift.toward` moves it toward that side.
- Tracks stay inside `min` to `max`: a `track` or `gain` change stops at the end of the track. `pay` fails when the track holds less than the amount. (This tool does not run effects. These are rules for the engine to implement.)
- `markerSet` sets a mutable space attribute (a marker). Markers start from `setup.spaceAttributes`. Example: Tan War Martial Law (`crown.martial-law`) sets `curfew` to `true`; every space starts with `curfew: false`.
- With 3 or 4 factions a bot names its enemy through an opponent table, never by faction order. `card.lowersEnemy` means the card hurts at least one enemy faction.
- A bot never asks the player to pick: every action node chooses through a priority table, ties go to the lettered tie-breaks and then to `randomization`.
- Each dry run states the board change (`patch`) from setup and the expected `outcome`, `path`, `chosen` spaces, `side` and `linked` result.
- 1.5.0: an engine tries a `linked` list in order, runs an action node's `parts` by rules 1 to 8 in "Bot decision graph", lets `bot.scoring` tables choose in scoring phases, and reads `card.lasting` from the side the bot plays. A dry run with case `scoring` runs the named scoring phases, not the decision graph.
- 1.6.0: a player picks one `choose` option; an engine running a bot action node with a target (`$target`) takes the option whose `faction` is that target, else the first option, and picks only spaces that also meet the `legal` of that option.
